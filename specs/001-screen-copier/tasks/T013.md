# T013: Concurrency, retry/backoff, ordering, offline, auth pause

## Goal
When this task is done, `src/screen_copier/recognition/queue.py` provides `RecognitionQueue(QObject)`, which runs an injected `Recognizer` concurrently on a thread pool with a configurable limit, retries temporary failures with exponential backoff, retries an unreadable response once, pauses on an authentication error, detects and recovers from being offline, and releases results to the stitcher strictly in capture order. T014 connects it to the controller.

## Acceptance criteria
- Given 10 submitted frames, a fake recognizer that takes 200 ms per call and `max_concurrent = 3`, When the queue runs, Then at no point are more than 3 calls in flight.
- Given frames 1, 2 and 3 whose recognitions complete in the order 3, 1, 2, When the queue runs, Then `result_ready` fires in the order 1, 2, 3.
- Given frame 1 ends up `failed` while frames 2 and 3 succeed, When the queue runs, Then `result_ready` fires for 2 and 3 once frame 1 is marked failed.
- Given a recognizer returning `Retryable`, `Retryable`, then `Ok`, When the queue runs with a fake sleep, Then the frame ends `recognized` and the recorded waits are ≥1 s and then ≥2 s.
- Given a recognizer returning `Retryable` on 5 consecutive attempts, When the queue runs, Then `frame_status` reports `failed` for that frame; When `retry(seq)` is called, Then the frame is submitted again.
- Given a recognizer returning `AuthError`, When the queue runs, Then the queue pauses, the frame's status is `queued` with `attempts` not incremented, `auth_required` fires exactly once, and after `resume()` the frame is recognized.
- Given a recognizer returning `Malformed` twice, When the queue runs, Then the frame is `failed` with the error `Unreadable model response`.
- Given a recognizer returning `Retryable(connection_error=True)` 3 times in a row, When the queue runs, Then `offline_changed(True)` is emitted; Given the next outcome is `Ok`, Then `offline_changed(False)` is emitted.
- Given an in-flight frame, When `discard(seq)` is called before its recognizer call returns, Then its result is ignored, no `result_ready` fires for it, and later frames are not blocked.
- Given two `Ok` outcomes with usage (10, 5) and (20, 7), When the queue runs, Then `usage` is emitted with the running totals, ending at (30, 12).
- Given a recognizer returning `BadRequest`, When the queue runs, Then the frame is `failed` at once with the API message and no retry happens.

## Notes for the worker
This is the one recognition module allowed to use Qt signals (AGENTS.md); keep the rest of the package pure. Implement the RecognitionQueue contract verbatim: constructor `RecognitionQueue(recognizer, *, max_concurrent, clock, sleep, rng)`, methods `submit`, `discard`, `retry`, `pause`, `resume`, `shutdown`, and signals `frame_status(seq, status, error)`, `result_ready(seq, FrameResult)`, `auth_required()`, `offline_changed(bool)`, `usage(input_tokens, output_tokens)`. Use a `concurrent.futures.ThreadPoolExecutor` sized `max_concurrent` for the HTTP calls and emit signals so they are delivered on the GUI thread (queued connections). Backoff delays are 1, 2, 4, 8, 16 s times `(1 + rng.uniform(0, 0.2))`; after 5 failed attempts the frame is `failed`. `Malformed` gets one retry, then `failed("Unreadable model response")`. `AuthError` pauses the whole queue, puts the frame back to `queued` without counting the attempt and emits `auth_required` once per pause. Offline: 3 consecutive connection errors set offline and emit `offline_changed(True)`; keep retrying the oldest frame every 15 s and hold the others; the first success clears it. In-order release: buffer results and fire `result_ready` only when every lower seq is recognized, failed or discarded. Discard cancels a future that has not started, otherwise its result is dropped when it arrives. Emit `frame_status` on every transition (`queued`, `recognizing`, `recognized`, `failed`). Clock, sleep and RNG are injected, so tests use a fake sleep that records waits and never wait in real time. Background: [architecture.md §7.4](../../../docs/architecture.md#74-queue-recognitionqueuepy) and [§4](../../../docs/architecture.md#4-threading-model). T009 and T012 run in parallel; stay inside `recognition/queue.py` and `tests/recognition/test_queue.py`.
